# ecdsa_lattice_ml

A research and teaching codebase for studying the combinatorial structure of
ECDSA over secp256k1, and for costing a **hypothetical** Hidden Number Problem
(HNP) lattice attack that assumes an oracle leaking the leading bits of each
signature nonce.

Version 1.1.1. See `CHANGELOG.md` for the audit fixes behind this release.

> ⚠️ **NOTICE:** This project is under active research and development,
> so some files **may not be added in time**.

---

## 1. Scope and honest framing

Read this section before interpreting any number this project prints.

**What the code does:**

- Implements the elliptic-curve group law, key generation, ECDSA signing and
  verification, and RFC 6979 deterministic nonces, from scratch, on two
  parameter sets: real secp256k1, and `toy-p31r1`, a 31-bit fixture curve (§3.3.1).
- Traces the double-and-add ladder and records every intermediate point (the
  "topology"), then derives combinatorial descriptors from that trace.
- Computes the exact conditional distribution of a nonce's decimal length given
  its first two decimal digits.
- Evaluates a closed-form cost model for a two-filter subset HNP lattice attack
  under an assumed nonce-bit leak.

**What the code does NOT do, and why it matters:**

- **There is no machine-learning model.** `generate_transaction_list.py`
  contains a *simulation*: a shuffled boolean mask sized to a target accuracy
  supplied via `--ml-exp-accuracy`. The quantity it "predicts", `str(k)[:2]`, is
  derived from the **secret** nonce, which an attacker never observes. Accuracy
  is therefore an **input assumption**, not a measurement. The real hook is
  still a `# TODO`.
- **Recovering leading bits of `k` from public data is ECDLP.** Since
  `r = (k·G).x mod n`, extracting partial information about `k` from
  `(r, s, z, Q)` is exactly a (partial) elliptic-curve discrete logarithm
  problem. Nothing here attempts it. Every figure produced by
  `ecdsa_attack_complexity.py` is conditional on that assumption holding.
- **The magnitude predictor is a documented negative result.** It is a constant
  function dressed up as a predictor; see §5.3.
- **The topology descriptors require the secret.** Building the ladder trace
  presupposes knowing the scalar. They describe a computation, not an attack
  surface reachable by an adversary.

The HNP lattice technique itself is decades-old published academic work
(Howgrave-Graham & Smart 2001; Nguyen & Shparlinski 2002/2003). This repository
implements **no lattice reduction**; it only evaluates a cost formula.

**Bottom line:** this project demonstrates no vulnerability in secp256k1. It is
a simulation whose hardest step is assumed rather than performed.

Both parameter sets are short Weierstrass curves over a prime field:

```text
E : y² = x³ + a·x + b   over  F_p,   with  4a³ + 27b² ≠ 0
```

The set of affine points plus a point at infinity `O` forms an abelian group of
order `n` (here prime, so the cofactor is 1), generated by `G`.

### 3.2 Group law

Implemented in `Secp256k1.point_add`. For `P₁ = (x₁, y₁)`, `P₂ = (x₂, y₂)`:

| Case | Result |
| --- | --- |

```text
V ← 0x01 × 32
K ← 0x00 × 32
K ← HMAC(K, V ‖ 0x00 ‖ int2octets(d) ‖ bits2octets(H(m)))
V ← HMAC(K, V)
K ← HMAC(K, V ‖ 0x01 ‖ int2octets(d) ‖ bits2octets(H(m)))
V ← HMAC(K, V)
loop:
  T ← ""
  while len(T) < rolen: V ← HMAC(K, V); T ← T ‖ V
  c ← bits2int(T)
  if 1 ≤ c < n: yield c
  K ← HMAC(K, V ‖ 0x00);  V ← HMAC(K, V)     # rejection / next-candidate path
```

Modular inverses use `pow(k, -1, p)` (Fermat/extended Euclid via CPython).

**Point at infinity is represented by `None`, and only by `None`.** This is a
deliberate invariant; a prior version also returned `(0, 0)`, which lies on
neither curve and leaked silently into callers.

### 3.3 The two parameter sets

Defined in `ecurve/secp256k1.py` as frozen `CurveParams` dataclasses.

| Field | `TEST_PARAMS` | `LEGACY_PARAMS` |
| --- | --- | --- |
| `name` | `toy-p31r1` | `secp256k1` |
| `mode` | `test` | `legacy` |
| `p` | `1241690119` (31 bits) | `2²⁵⁶ − 2³² − 977` (256 bits) |
| `a`, `b` | `1`, `35` | `0`, `7` |
| `n` | `1241630743` (prime, 31 bits) | secp256k1 order (prime, 256 bits) |
| `p − n` | `59376` | `4.32e38` |
| `l` | `29` | `254` |
| Nonce source | `random.randrange` | RFC 6979 |
| Message hash | randomised (see below) | double-SHA256 of a Bitcoin sighash preimage |

**Verified invariants** (all checked in `tests/test_fixes.py`): `G` lies on the
curve, `n·G = O`, `n` is prime, and the Frobenius trace `t = p + 1 − n = 59377`
satisfies the Hasse bound `|t| ≤ 2√p ≈ 70474` for the toy curve.

**On the name `toy-p31r1`.** It follows SEC nomenclature: prime field, 31 bits,
`r` for a verifiably-random (non-Koblitz) curve, first of its kind. The `r` is
load-bearing — Koblitz curves are the `a = 0` family that secp256k1 belongs to,
and this curve's `a = 1` is exactly what earns it its keep (see below).
`LEGACY_PARAMS` is the only real secp256k1 here; nothing in the code branches on
`name`, which appears solely in report headers.

`mode` — not `name` — is what selects behaviour throughout the codebase.

#### 3.3.1 Why the toy curve exists

It is a **test fixture**, not an alternative research target. It earns its place
by catching two classes of defect that secp256k1 **structurally cannot**.
Measured by mutation testing (inject a plausible bug, give each curve an equal
~0.4 s budget, see which notices):

| Injected defect | `toy-p31r1` | `secp256k1` |
| --- | --- | --- |
| Drop `+ a` from the doubling slope | **caught** | **never caught** |
| `r_y = y % n` (the real bug B6) | **caught** | **never caught** |
| Drop `x₂` from `x₃ = λ² − x₁ − x₂` | caught | caught |

1. **The `a` blind spot is permanent, not probabilistic.** secp256k1 has
   `a = 0`, so `3x² + a` is identically `3x²`. Any defect in handling `a` is
   invisible on the real curve *no matter how many trials you run*. `toy-p31r1`
   has `a = 1` and is the only thing in this repository exercising that term.
2. **The `p − n` gap makes coordinate bugs reachable.** With `p − n = 59376`,
   `P(coordinate ≥ n) ≈ 4.78e−5` — about 1 in 20,912 signatures, i.e. seconds of
   wall-clock. On secp256k1 the same event sits at `≈ 3.73e−39`, an expected wait
   of ~2.7e38 years. Bug B6 was findable *only* because this curve exists.
3. **Speed.** ~8,810 sign/s and ~5,369 verify/s versus ~125 and ~58 on
   secp256k1 (70× and 93×). 12 of the 29 regression tests run on it for that
   reason.

The cost is real and worth stating: `mode` branching appears in ~10 places, the
nonce source and message hash differ between modes, and RFC 6979 is therefore
exercised only on `legacy`. Those are known warts, not accidents — see §8.

### 3.4 Key generation

```text
d  ←$  [1, n−1]        (rejection sampling over secrets.randbits, no modulo bias)
Q  =   d · G
```

`Secp256k1._generate_private_key` draws `n.bit_length()` random bits and rejects
anything outside `[1, n−1]`, so the distribution is provably uniform.

### 3.5 Scalar multiplication (double-and-add)

`Secp256k1.scalar_multiply` is a right-to-left binary ladder:

```text
Q ← O
while k:
    if k & 1: Q ← Q + P        # logged with op = "1"
    k ← k >> 1
    if k:     P ← P + P        # logged with op = ""   (final doubling skipped)
```

This is **not** constant-time and makes no attempt to be. It is an analysis
instrument, not a production primitive: the whole point is that its operation
sequence is observable and recorded.

### 3.6 ECDSA

**Sign** (`sign_message`), for message `m` and key `d`:

```text
z  = H(m) mod n
k  ← nonce candidate stream        (RFC 6979 for legacy; random for test)
(x, y) = k · G
r  = x mod n                       retry if r = 0
s  = k⁻¹ · (z + r·d) mod n         retry if s = 0
return (z, r, y, s, k, k⁻¹)
```

**Verify** (`verify_signature`):

```text
reject unless 1 ≤ r < n and 1 ≤ s < n
w  = s⁻¹ mod n
u₁ = z·w mod n,  u₂ = r·w mod n
R  = u₁·G + u₂·Q                   reject if R = O
accept iff  R.x mod n = r
```

**Signature tuple convention.** `sign_message` returns
`(z, r_x, r_y, s, k, k_inv)` where:

- `r_x = (k·G).x mod n` — the ECDSA `r`, reduced mod `n` **by definition**;
- `r_y = (k·G).y mod p` — the **raw** affine ordinate, deliberately *not*
  reduced mod `n` (reducing it is meaningless: `y` lives mod `p`).

Because `r_x` must be reduced but the topology log stores coordinates mod `p`,
comparing `(r_x, r_y)` against topology rows mismatches whenever `x ≥ n`.
Callers that need to match the ladder must use `Secp256k1.last_nonce_point`,
which exposes the untouched `k·G` (both coordinates mod `p`), cached during
signing at no extra scalar multiplication.

### 3.7 RFC 6979 deterministic nonces

`_rfc6979_k_candidates` implements RFC 6979 §3.2 as a **generator**, using
HMAC-SHA256:

```text
V ← 0x01 × 32
K ← 0x00 × 32
K ← HMAC(K, V ‖ 0x00 ‖ int2octets(d) ‖ bits2octets(H(m)))
V ← HMAC(K, V)
K ← HMAC(K, V ‖ 0x01 ‖ int2octets(d) ‖ bits2octets(H(m)))
V ← HMAC(K, V)
loop:
  T ← ""
  while len(T) < rolen: V ← HMAC(K, V); T ← T ‖ V
  c ← bits2int(T)
  if 1 ≤ c < n: yield c
  K ← HMAC(K, V ‖ 0x00);  V ← HMAC(K, V)     # rejection / next-candidate path
```

Two points of correctness worth stating explicitly:

1. **Rejection, not reduction.** The standard mandates `bits2int(T)` followed by
   rejecting out-of-range candidates. Reducing `mod n` instead would introduce a
   (tiny, ~2⁻¹²⁸, but real) modulo bias — precisely the class of nonce bias this
   project purports to study.
2. **`bits2octets` collapses to `z` on secp256k1.** Since `2²⁵⁵ < n < 2²⁵⁶`, any
   256-bit hash satisfies `H(m) < 2n`, so the spec's conditional subtraction and
   the reduction `H(m) mod n` coincide. Passing the already-reduced `z` is
   therefore RFC-correct *here*, though it would not be on a curve where
   `H(m) ≥ 2n` is possible.

Exposing candidates as a stream is what makes caller-side rejection safe: RFC
6979 is deterministic in `(d, z)`, so naively re-deriving `k` after a rejection
loops forever. Advancing the ladder is the mechanism RFC 6979 §3.6 prescribes.

**Validated against the official RFC 6979 + SHA-256 test vectors for secp256k1
(5/5).**

### 3.8 Bitcoin sighash preimages

For `LEGACY_PARAMS`, the message signed is a real Bitcoin signature hash
preimage, so `z` is bound to transaction semantics:

- `make_bitcoin_legacy_sighash_message` — legacy SIGHASH_ALL for a 1-in/1-out
  P2PKH spend. Note it does **not** commit to the input value; that omission is
  the flaw BIP 143 exists to fix.
- `make_bitcoin_segwit_sighash_message` — BIP 143 SegWit v0 SIGHASH_ALL for
  P2WPKH, committing to `hashPrevouts`, `hashSequence`, the spent output's
  value, and `hashOutputs`.

`hash160 = RIPEMD160(SHA256(·))` is required for both. Since OpenSSL 3.x moved
RIPEMD-160 into the legacy provider, `hashlib.new("ripemd160")` raises on many
distributions; `ecurve/_ripemd160.py` provides a pure-Python fallback, verified
against the official RIPEMD-160 vectors (including the one-million-`a` vector)
and fuzzed against `hashlib` across block boundaries.

For `TEST_PARAMS`, `hash_message` returns `random.randrange(1, n−1)` — `z` is
**not** bound to the message. This is intentional for the toy curve but means
test mode is not a signing oracle.

### 3.9 The "topology" trace

When `_trace_topology` is set, every `point_add` appends a row:

```text
[x₁, y₁, x₂, y₂, x₃, y₃, op]      op = "1" for an accumulator add, "" for a doubling
```

`get_double_points()` returns the fixed ladder basis
`[G, 2G, 4G, …, 2^(l+1)·G]` — that is `l + 2` points (31 for the toy curve, 256
for secp256k1).

`_prepare_topology_of_key` truncates the log at the **last** row whose `(x₃, y₃)`
equals the final result. (Searching forward for the *first* match risks stopping
at a coincidental doubling row.)

**A structural quirk you must know about.** `point_add(None, P)` short-circuits
with `return P` *before* a row is recorded. Consequently the very first set bit
of the scalar produces **no** log row, and

```python
recorded op="1" rows  =  popcount(k) − 1
```

Verified: for `d = 90 = 0b1011010`, popcount 4 → 3 recorded rows; for a 256-bit
key with popcount 128 → 127 recorded rows. The constant
`Secp256k1.UNRECORDED_LEADING_ADDS = 1` documents this.

### 3.10 `identify_condition` and `count_subsets`

`identify_condition` returns a string
`"{idx_x1y1_first}_{idx_x2y2_first}_{total_adds}_{idx_x2y2_last}"`, where the
indices are 1-based positions into `get_double_points()` and `total_adds` counts
recorded `op = "1"` rows.

`count_subsets` then computes:

```text
total_numbers    = idx_x2y2_last − idx_x2y2_first − idx_x1y1_first
combination_size = total_adds − 2                    (clamped at 0)
result           = C(total_numbers, combination_size)
```

Worked example, real secp256k1, `d` with popcount 128:

```text
condition        = "1_2_127_256"
total_numbers    = 256 − 2 − 1 = 253
combination_size = 127 − 2     = 125
C(253, 125)      ≈ 7.126e74
```

**Interpretive warning.** The `− 2` is a magic constant. One of the two is the
off-by-one from §3.9; the provenance of the other is undocumented in the
original code and this release does **not** change it, because doing so would
renumber every row of every existing report. More importantly: computing any of
this requires already knowing the scalar. Large binomials here indicate that the
ladder structure is not brute-forceable; they are **not** an attack cost.

### 3.11 Magnitude of a nonce from its leading digits (`k_magnitude.py`)

Let `D(k)` be the number of decimal digits of `k`, and let `lead ∈ [10, 99]` be
its first two decimal digits. For a uniform `k ∈ [1, n−1]`:

```text
count(d, lead) = |{ x ∈ [1, n−1] : D(x) = d, x starts with `lead` }|
               = max(0, min((lead+1)·10^(d−2) − 1, n−1) − max(lead·10^(d−2), 1) + 1)

P(D = d | lead)  =  count(d, lead) / Σ_{d'} count(d', lead)
```

computed exactly with `fractions.Fraction` (no floating point until the final
cast). The distribution is conditioned on `D(k) ≥ 2`, since the leading-*pair*
model is undefined for `k < 10`; for a 256-bit curve `P(k < 10) ≈ 1e−76`.

**The measured result, and why it is a negative one.** On real secp256k1
(`n` has 78 digits, starting `11`):

```markdown
| Leading pair | Predicted `D` | Probability |
|---|---|---|
| `12 … 99` (88 pairs) | 77 | 0.900 |
| `10` | 78 | 0.900 |
| `11` | 78 | 0.839 |
```

The predictor is essentially a **constant function**. Its ≈0.90 accuracy is the
base rate of "`n` has 78 digits, so 90% of values below it have 77" — it is the
prior, not information gained. Knowing `D(k) = 77` narrows `k` to a band of
width ≈ `10⁷⁶ ≈ 2²⁵³`, i.e. roughly **3 bits** of narrowing from a 256-bit
space, and each magnitude step carries `log₂10 ≈ 3.32` bits of residual
uncertainty. The same shape holds on the toy curve (87 pairs → `D = 9` at
p = 0.90).

This is why the module docstring states plainly that it is **not** a usable
nonce-bit predictor for correctly generated nonces — and it is the reason the
"decimal digits ⇒ leading binary bits" step assumed elsewhere does not hold.

### 3.12 The Hidden Number Problem and the cost model

**The mathematics being modelled** (not implemented here). From
`s·k ≡ z + r·d (mod n)`:

```text
k ≡ s⁻¹·r·d + s⁻¹·z  (mod n)
```

Write `t_i = s_i⁻¹·r_i` and `u_i = s_i⁻¹·z_i`, so `k_i ≡ t_i·d + u_i (mod n)`.
If an oracle pins `k_i` to an interval of width `n / 2^L`, then for known
constants `c_i`:

```text
| t_i·d + u_i − c_i |_n  <  n / 2^(L+1)
```

This is the Hidden Number Problem: `d` is hidden, and each signature is an
approximate relation. Given `m ≈ ⌈log₂n / L⌉` such relations, `d` is recoverable
as a short vector in a lattice of dimension ≈ `m + 1` (or `m + 2`), via LLL or
BKZ. **A single wrong interval poisons the entire lattice** — the reduction then
returns nothing.

**The cost model** in `ecdsa_attack_complexity.py`. A signature is *clean* iff
both assumed predictors are correct:

```text
p_clean = clamp( p_b·p_m + ρ·√(p_b(1−p_b)·p_m(1−p_m)),
                 lo = max(0, p_b + p_m − 1),
                 hi = min(p_b, p_m) )
```

with `ρ = 0` meaning independence (default; conservative *for the attacker*),
`ρ > 0` meaning the predictors fail together more often than chance. Then:

```text
m_req  = ⌈ ⌈curve_bits / L⌉ · safety_factor ⌉
dim    = m_req + dim_overhead
T_filt = ⌈ surplus · m_req / p_clean ⌉          usable pool
T_raw  = ⌈ T_filt / pass_rate ⌉                 raw signatures to collect
clean  = round(p_clean · T_filt)
runs   = C(T_filt, m_req) / C(clean, m_req)     expected subsets until all-clean
t/core = runs · t_per_run_sec / cores
```

The `runs` expression is the reciprocal of the probability that a uniformly
drawn `m_req`-subset of the pool is entirely clean — the model is "keep drawing
subsets until one contains no poisoned signature". Binomials are evaluated in
log space via `lgamma` to avoid overflow. Parallelism is **linear and tight**:
each reduction is independent, with no inter-core communication.

Defaults: `curve_bits=256`, `leak_bits=[6]`, `safety_factor=1.3`, `surplus=2.0`,
`p_mag=89.5`, `correlation=0.0`, `filter_pass_rate=1.0`, `dim_overhead=2`,
`cores=[1]`.

**`t_per_run_sec` is the single most important number in the model and it is not
measured here.** If omitted, a dim-dependent heuristic
`base · e^(growth·(dim − ref_dim))` supplies an order-of-magnitude placeholder
only. Calibrate it on your own hardware and solver (build a synthetic all-clean
HNP instance of dimension `m_req + 2`, run one `fpylll` LLL/BKZ reduction, take
wall-clock) and pass `--t-per-run-sec`.

**And the load-bearing caveat, restated:** `p_b` — the probability the nonce-bit
oracle is right — is a swept input, not a capability anyone has demonstrated.
§3.11 shows the magnitude channel supplies a fraction of a bit, not the `L = 6`
the default table assumes. The tables are a sensitivity analysis of a
hypothetical, not a forecast.

## 5. Usage

`--curve-mode` defaults to **`legacy`** (real secp256k1) everywhere it appears.
Pass `--curve-mode test` explicitly to select `toy-p31r1`; expect it to be ~70×
faster and to answer a different question (§3.3.1).

All 9 invocation modes below are exercised by the `test_A3_*` tests.

```bash
# Regression suite (no dependencies)
python3 tests/test_fixes.py
python3 -m pytest tests/ -q          # if pytest is installed

# Curve / sign / verify demo, standalone, as in the original project:
cd ecurve && python secp256k1.py > secp256k1.txt

# ... or as a module, from the repository root:
python3 -m ecurve.secp256k1

# Magnitude distribution on secp256k1 (§3.11); --curve-mode defaults to legacy:
python3 -m ecurve.k_magnitude                     # all leading pairs 10..99
python3 -m ecurve.k_magnitude --digits 47
python3 -m ecurve.k_magnitude --curve-mode test   # toy-p31r1, for comparison

# Signature corpus on real secp256k1, fixed key, BIP 143 preimages:
python3 generate_transaction_list.py \
        --private-key 64389052532870313044990203562685705333461655978490098671693221677551702405611 \
        --tx-per-key 5 --sig-type p2wpkh --outdir out

# Same, on the toy curve — fast, reproducible via --seed:
python3 generate_transaction_list.py --curve-mode test --keys 3 \
        --tx-per-key 20 --seed 42 --outdir out

# Cost model — heuristic timing (uncalibrated, order-of-magnitude only):
python3 ecdsa_attack_complexity.py

# Cost model — calibrated, several core counts, CSV out:
python3 ecdsa_attack_complexity.py --t-per-run-sec 2.0 --cores 1 8 64 \
        --leak-bits 4 6 8 --csv complexity.csv
```

Key flags for `generate_transaction_list.py`: `--curve-mode {test,legacy}` (default
`legacy`),
`--private-key`, `--keys`, `--tx-per-key`, `--min-start-range`,
`--ml-exp-accuracy`, `--seed`, `--outdir`, `--demo`, `--sig-type {p2pkh,p2wpkh}`.

## 6. Report format

`generate_transaction_list.py` writes
`transaction_list_<YYYYMMDDHHMMSS>.txt`: curve parameters, the signing formulas,
an explicit warning that the predictor is simulated, then a fixed-width table
with 14 columns:

```text
s, z, r(x), r(y), d*, k*, k^(-1)*, condition*,
ml_exp_k_val, ml_act_k_val, ml_match_k_val,
ml_exp_k_mag, ml_act_k_mag, ml_match_k_mag
```

Columns marked `*` are secret or secret-derived and exist only because this is a
simulation with full knowledge. `condition*` is the §3.10 descriptor.

The statistics block reports the effective key count, transactions per key, the
**actual** number of rows generated, the tuple-space cardinality `(n−1)⁴`
(a combinatorial ceiling, *not* a security bound), the assumed vs. realised
predictor accuracies, the observed distribution of decimal lengths of `k` as
`Case D<n> Count`, and elapsed time.

Accuracy is computed as `matches / len(rows)`. If it drifts from
`--ml-exp-accuracy`, that is sampling noise, nothing more — the mask is
constructed to hit the target exactly.

## 7. Verified invariants

Enforced by `tests/test_fixes.py` (29 tests, all passing):

- RFC 6979: 5/5 official secp256k1 + SHA-256 test vectors.
- RIPEMD-160: all official vectors, plus fuzzing against `hashlib` across block
  boundaries.
- `verify(sign(m)) = True` on both curves over repeated trials.
- Generated public keys lie on the curve, on both parameter sets.
- `n·G = O`; `scalar_multiply` returns `None` (never `(0,0)`) for infinity.
- `P + (−P) = O` returns `None` and `verify_signature` survives it.
- `magnitude_distribution` sums to 1; `k_magnitude` doctests pass.
- Argument validation rejects every out-of-range input listed in `CHANGELOG.md` §D.
- All 9 invocation modes import and run.

## 8. Known limitations

- **Not constant-time, not side-channel resistant, not production code.** The
  ladder is deliberately observable (§3.5). Do not use any of this to protect
  real funds.
- Test-mode `z` is not bound to the message (§3.8), so `mode="test"` is not a
  signing oracle. This also means the toy curve cannot exercise RFC 6979, which
  leaves the most delicate cryptographic code in the repository covered only by
  the 70×-slower curve (§3.3.1).
- `mode` branching appears in ~10 places; each is a site where the two curves can
  drift apart.
- The `− 2` in `count_subsets` is a preserved magic constant (§3.10).
- `maximum_transaction_count = (n−1)⁴` has no defined security meaning.
- The cost model's `t_per_run_sec` is uncalibrated unless you pass it (§3.12).
- **The predictor is simulated (§1).** This is not a code defect to be patched;
  it is the methodological boundary of the project.
