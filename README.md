# ecdsa_lattice_ml

Investigation of ECDSA state spaces, lattice-based cryptanalysis, and
ML applications in predicting hidden cryptographic meta-invariants.

> ⚠️ **NOTICE:** This project is under active research and development,
> so some files **may not be added in time**.

---

## 1. Scope and honest framing

Read this section before interpreting any number this project prints.

**What the code does:**

- Implements the elliptic-curve group law, key generation, ECDSA signing and
  verification, and RFC 6979 deterministic nonces, from scratch, on two
  parameter sets: real secp256k1, and `secp17k1`, a 17-bit fixture curve (§3.3.1).
- Computes the exact conditional distribution of a nonce's decimal length given
  its first two decimal digits.
- Evaluates a cost model for a two-predictor subset HNP lattice attack under an
  assumed nonce-bit leak, reporting a distribution of reduction counts rather
  than a single figure (§3.10).

**What the code does NOT do, and why it matters:**

- **There is no machine-learning model.** `generate_transaction_list.py`
  contains a *simulation*: a shuffled boolean mask sized to a target accuracy
  supplied via `--ml-exp-accuracy`. The quantity it "predicts", `str(k)[:2]`, is
  derived from the **secret** nonce, which an attacker never observes. Accuracy
  is therefore an **input assumption**, not a measurement. The real hook is
  still a `# TODO`.
- **Recovering leading bits of `k` from public data is ECDLP.** Since
  `r = (k·G).x mod n`, extracting partial information about `k` from
  `(r, s, z, Q)` is exactly a (partial) elliptic-curve discrete logarithm
  problem. Nothing here attempts it. Every figure produced by
  `ecdsa_attack_complexity.py` is conditional on that assumption holding.
- **The magnitude predictor is a documented negative result.** It is a constant
  function dressed up as a predictor; see §3.9.

The HNP lattice technique itself is decades-old published academic work
(Howgrave-Graham & Smart 2001; Nguyen & Shparlinski 2002/2003). This repository
implements **no lattice reduction**; it only evaluates a cost formula.

**Bottom line:** this project demonstrates no vulnerability in secp256k1. It is
a simulation whose hardest step is assumed rather than performed.

## 3. Mathematical background

### 3.1 Curves and the group

Both parameter sets are short Weierstrass curves over a prime field:

```text
E : y² = x³ + a·x + b   over  F_p,   with  4a³ + 27b² ≠ 0
```

The set of affine points plus a point at infinity `O` forms an abelian group of
order `n` (here prime, so the cofactor is 1), generated by `G`. Scalar
multiplication `k·G` is defined in §3.5.

### 3.2 Group law

Implemented in `Secp256k1.point_add`. For `P₁ = (x₁, y₁)`, `P₂ = (x₂, y₂)`:

- If either point is `None` (point at infinity), return the other.
- If `x₁ = x₂` and `(y₁ + y₂) ≡ 0 (mod p)`, return `None` (the points are
  additive inverses; this also covers the order-2 case `y₁ = y₂ = 0`).
- If `x₁ = x₂` (doubling):  
  `λ = (3x₁² + a) · (2y₁)⁻¹ mod p`,  
  `x₃ = λ² − 2x₁ mod p`,  
  `y₃ = λ(x₁ − x₃) − y₁ mod p`.
- Otherwise (addition):  
  `λ = (y₂ − y₁) · (x₂ − x₁)⁻¹ mod p`,  
  `x₃ = λ² − x₁ − x₂ mod p`,  
  `y₃ = λ(x₁ − x₃) − y₁ mod p`.

Modular inverses use `pow(k, -1, p)` (Fermat/extended Euclid via CPython).

**Point at infinity is represented by `None`, and only by `None`.** This is a
deliberate invariant; a prior version also returned `(0, 0)`, which lies on
neither curve and leaked silently into callers.

### 3.3 The two parameter sets

Defined in `ecurve/secp256k1.py` as frozen `CurveParams` dataclasses.

| Field | `TEST_PARAMS` | `LEGACY_PARAMS` |
| --- | --- | --- |
| `name` | `secp17k1` | `secp256k1` |
| `mode` | `test` | `legacy` |
| `p` | `100003` (17 bits) | `2²⁵⁶ − 2³² − 977` (256 bits) |
| `a`, `b` | `0`, `2` | `0`, `7` |
| `n` | `99667` (prime, 17 bits) | secp256k1 order (prime, 256 bits) |
| `p − n` | `336` | `4.32e38` |
| Frobenius trace `t = p + 1 − n` | `337` (Hasse bound `2√p = 632`) | `4.32e38` (bound `6.81e38`) |
| Nonce source | `random.randrange` | RFC 6979 |
| Message hash | randomised (see below) | double-SHA256 of a Bitcoin sighash preimage |

**Verified invariants.** `G` lies on the curve, `n·G = O`, `(n−1)·G = −G`, `n`
and `p` are prime (Miller-Rabin — trial division cannot reach a 256-bit order),
the curve is non-singular (`4a³ + 27b² ≠ 0`), and the Hasse bound holds. These
run on **both** parameter sets under `test_G1` … `test_G7`.

They are listed here because an earlier revision of this README claimed they
were "all checked in tests/" when **none of them were**: the suite tested
behaviour built on the curve without ever checking the curve itself. That gap
went unnoticed until `TEST_PARAMS` was swapped — precisely the event where it
matters.

`LEGACY_PARAMS` is the only real secp256k1 here; nothing in the code branches on
`name`, which appears solely in report headers. `mode` — not `name` — is what
selects behaviour throughout the codebase.

#### 3.3.1 Why the test curve exists

It is a **test fixture**, not an alternative research target. Measured by
mutation testing (inject a plausible bug, run the suite, see which tests
notice):

| Injected defect | `secp17k1` | `secp256k1` |
| --- | --- | --- |
| `r_y = y % n` (the real bug B6) | **caught** | **never caught** |
| Drop `x₂` from `x₃ = λ² − x₁ − x₂` | caught | caught |
| Drop `+ a` from the doubling slope | never caught | never caught |

The last row is not a coverage gap — it is caught, but by neither curve. See
point 3 below and §7.2.

1. **The `p − n` gap makes coordinate bugs reachable.** With `p − n = 336`,
   `P(coordinate ≥ n) ≈ 3.36e−3` — about 1 in 298 signatures, so `test_B6` now
   *requires* the event rather than hoping for it: 5000 signatures miss it with
   probability ≈ 5e−8. On secp256k1 the same event sits at `≈ 3.73e−39`, an
   expected wait of ~7e28 years at the measured signing rate. Bug B6 was
   findable *only* because a small curve exists.
2. **Speed.** ~26,800 sign/s and ~16,800 verify/s versus ~125 and ~63 on
   secp256k1 (214× and 266×). 29 of the 78 regression tests touch a small
   curve for that reason, and the whole suite runs in about one second.
3. **What it does NOT cover.** `secp17k1` has `a = 0`, exactly like secp256k1.
   The `+ a` term in the doubling slope is therefore dead code on both shipped
   curves — a **permanent** blind spot, not a probabilistic one, since
   `3x² + 0` is identically `3x²` no matter how many trials are run. The
   previous test curve carried `a = 1` and was the only thing exercising that
   term; the swap silently removed the coverage.

   Rather than introduce a third curve, `test_G9` covers the term
   *differentially*: it perturbs the `a` field of an existing parameter set,
   then requires that `point_add` matches an independent reference which keeps
   the term and diverges from the same reference with the term dropped. Nothing
   claims the perturbed parameters form a valid curve, and nothing is signed on
   them — the assertion is only about whether the implementation reads
   `curve.a` and places it correctly. This catches subtle corruptions too
   (`3x² + 2a`, `3x² − a`), each of which is invisible to every other test in
   the suite.

   What it still does **not** cover, and only a genuine `a ≠ 0` curve would:
   that the group law's *invariants* survive `a ≠ 0` — that doubling lands back
   on the curve, agrees with `scalar_multiply`, and respects the order.
   `test_G9b` records that residual gap and will flip to a skip if
   `TEST_PARAMS` ever gains a non-zero `a`.

The cost is real and worth stating: `mode` branching appears in ~10 places, the
nonce source and message hash differ between modes, and RFC 6979 is therefore
exercised only on `legacy`. Those are known warts, not accidents — see §8.

### 3.4 Key generation

```text
d  ←$  [1, n−1]        (rejection sampling over secrets.randbits, no modulo bias)
Q  =   d · G
```

`Secp256k1._generate_private_key` draws `n.bit_length()` random bits and rejects
anything outside `[1, n−1]`, so the distribution is provably uniform.

### 3.5 Scalar multiplication (double-and-add)

`Secp256k1.scalar_multiply` is a right-to-left binary ladder:

```text
Q ← O
while k:
    if k & 1: Q ← Q + P
    k ← k >> 1
    if k:     P ← P + P        # final doubling skipped
```

This is **not** constant-time and makes no attempt to be. It is an analysis
instrument, not a production primitive: the whole point is that its operation
sequence is observable and recorded.

### 3.6 ECDSA

**Sign** (`sign_message`), for message `m` and key `d`:

```text
z  = H(m) mod n
k  ← nonce candidate stream        (RFC 6979 for legacy; random for test)
(x, y) = k · G
r  = x mod n                       retry if r = 0
s  = k⁻¹ · (z + r·d) mod n         retry if s = 0
return (z, r, y, s, k, k⁻¹)
```

**Verify** (`verify_signature`):

```text
reject unless 1 ≤ r < n and 1 ≤ s < n
w  = s⁻¹ mod n
u₁ = z·w mod n,  u₂ = r·w mod n
R  = u₁·G + u₂·Q                   reject if R = O
accept iff  R.x mod n = r
```

**Signature tuple convention.** `sign_message` returns
`(z, r_x, r_y, s, k, k_inv)` where:

- `r_x = (k·G).x mod n` — the ECDSA `r`, reduced mod `n` **by definition**;
- `r_y = (k·G).y mod p` — the **raw** affine ordinate, deliberately *not*
  reduced mod `n` (reducing it is meaningless: `y` lives mod `p`).

### 3.7 RFC 6979 deterministic nonces

`_rfc6979_k_candidates` implements RFC 6979 §3.2 as a **generator**, using
HMAC-SHA256:

```text
V ← 0x01 × 32
K ← 0x00 × 32
K ← HMAC(K, V ‖ 0x00 ‖ int2octets(d) ‖ bits2octets(H(m)))
V ← HMAC(K, V)
K ← HMAC(K, V ‖ 0x01 ‖ int2octets(d) ‖ bits2octets(H(m)))
V ← HMAC(K, V)
loop:
  T ← ""
  while len(T) < rolen: V ← HMAC(K, V); T ← T ‖ V
  c ← bits2int(T)
  if 1 ≤ c < n: yield c
  K ← HMAC(K, V ‖ 0x00);  V ← HMAC(K, V)     # rejection / next-candidate path
```

Two points of correctness worth stating explicitly:

1. **Rejection, not reduction.** The standard mandates `bits2int(T)` followed by
   rejecting out-of-range candidates. Reducing `mod n` instead would introduce a
   (tiny, ~2⁻¹²⁸, but real) modulo bias — precisely the class of nonce bias this
   project purports to study.
2. **`bits2octets` collapses to `z` on secp256k1.** Since `2²⁵⁵ < n < 2²⁵⁶`, any
   256-bit hash satisfies `H(m) < 2n`, so the spec's conditional subtraction and
   the reduction `H(m) mod n` coincide. Passing the already-reduced `z` is
   therefore RFC-correct *here*, though it would not be on a curve where
   `H(m) ≥ 2n` is possible.

Exposing candidates as a stream is what makes caller-side rejection safe: RFC
6979 is deterministic in `(d, z)`, so naively re-deriving `k` after a rejection
loops forever. Advancing the ladder is the mechanism RFC 6979 §3.6 prescribes.

**Validated against the official RFC 6979 + SHA-256 test vectors for secp256k1**
(3/3 exercised by the regression suite). The check is at the candidate-generator
level: `_rfc6979_k_candidates` reproduces the published `k` when driven by the
vector's message hash, i.e. a **single** SHA-256. The Bitcoin signing path in
this repo instead derives `z` via **double** SHA-256 of a sighash preimage
(§3.6, §3.8), so end-to-end `sign_message` output matches bitcoin-core nonces
rather than the single-hash vectors — the two differ only in the message-hash
step, not in the RFC 6979 ladder itself.

### 3.8 Bitcoin sighash preimages

For `LEGACY_PARAMS`, the message signed is a real Bitcoin signature hash
preimage, so `z` is bound to transaction semantics:

- `make_bitcoin_legacy_sighash_message` — legacy SIGHASH_ALL for a 1-in/1-out
  P2PKH spend. Note it does **not** commit to the input value; that omission is
  the flaw BIP 143 exists to fix.
- `make_bitcoin_segwit_sighash_message` — BIP 143 SegWit v0 SIGHASH_ALL for
  P2WPKH, committing to `hashPrevouts`, `hashSequence`, the spent output's
  value, and `hashOutputs`.

`hash160 = RIPEMD160(SHA256(·))` is required for both. Since OpenSSL 3.x moved
RIPEMD-160 into the legacy provider, `hashlib.new("ripemd160")` raises on many
distributions; `ecurve/_ripemd160.py` provides a pure-Python fallback, verified
against the official RIPEMD-160 vectors (including the one-million-`a` vector)
and fuzzed against `hashlib` across block boundaries.

For `TEST_PARAMS`, `hash_message` returns `random.randrange(1, n−1)` — `z` is
**not** bound to the message. This is intentional for the test curve but means
test mode is not a signing oracle.

### 3.9 Magnitude of a nonce from its leading digits (`k_magnitude.py`)

Let `D(k)` be the number of decimal digits of `k`, and let `lead ∈ [10, 99]` be
its first two decimal digits. For a uniform `k ∈ [1, n−1]`:

```text
count(d, lead) = |{ x ∈ [1, n−1] : D(x) = d, x starts with `lead` }|
               = max(0, min((lead+1)·10^(d−2) − 1, n−1) − max(lead·10^(d−2), 1) + 1)

P(D = d | lead)  =  count(d, lead) / Σ_{d'} count(d', lead)
```

computed exactly with `fractions.Fraction` (no floating point until the final
cast). The distribution is conditioned on `D(k) ≥ 2`, since the leading-*pair*
model is undefined for `k < 10`; for a 256-bit curve `P(k < 10) ≈ 1e−76`.

**The measured result, and why it is a negative one.** On real secp256k1
(`n` has 78 digits, starting `11`):

| Leading pair | Predicted `D` | Probability |
| --- | --- | --- |
| `12 … 99` (88 pairs) | 77 | 0.900 |
| `10` | 78 | 0.900 |
| `11` | 78 | 0.839 |

The predictor is essentially a **constant function**. Its ≈0.90 accuracy is the
base rate of "`n` has 78 digits, so 90% of values below it have 77" — it is the
prior, not information gained. Knowing `D(k) = 77` narrows `k` to a band of
width ≈ `10⁷⁶ ≈ 2²⁵³`, i.e. roughly **3 bits** of narrowing from a 256-bit
space, and each magnitude step carries `log₂10 ≈ 3.32` bits of residual
uncertainty.

The same degenerate shape holds on `secp17k1` (`n = 99667`, 5 digits, begins
`99`), though the split differs: 89 of the 90 leading pairs predict `D = 5` at
p = 0.900, and the remaining pair `99` predicts `D = 5` at p = 0.857. Every pair
maps to the same magnitude here, because `n` sits near the top of the 5-digit
range — whereas secp256k1's `n` begins `11`, so its boundary pairs `10` and `11`
fall into a *different* magnitude. The exact numbers are curve-specific and are
pinned by the `k_magnitude` doctests, which must be updated whenever the test
curve changes; `test_E21b` pins the curve-independent part (one magnitude covers
at least 88 of the 90 pairs on any curve).

This is why the module docstring states plainly that it is **not** a usable
nonce-bit predictor for correctly generated nonces — and it is the reason the
"decimal digits ⇒ leading binary bits" step assumed elsewhere does not hold.

### 3.10 The Hidden Number Problem and the cost model

**The mathematics being modelled** (not implemented here). From
`s·k ≡ z + r·d (mod n)`:

```text
k ≡ s⁻¹·r·d + s⁻¹·z  (mod n)
```

Write `t_i = s_i⁻¹·r_i` and `u_i = s_i⁻¹·z_i`, so `k_i ≡ t_i·d + u_i (mod n)`.
If an oracle pins `k_i` to an interval of width `n / 2^L`, then for known
constants `c_i`:

```text
| t_i·d + u_i − c_i |_n  <  n / 2^(L+1)
```

This is the Hidden Number Problem: `d` is hidden, and each signature is an
approximate relation. Given `m ≈ ⌈log₂n / L⌉` such relations, `d` is recoverable
as a short vector in a lattice of dimension ≈ `m + 1` (or `m + 2`), via LLL or
BKZ. **A single wrong interval poisons the entire lattice** — the reduction then
returns nothing.

**The cost model** in `ecdsa_attack_complexity.py`. A signature is *clean* iff
both assumed predictors are correct. How the two are combined depends on how
`p_m` is defined, and the two definitions must not be mixed:

```text
--p-mag-mode conditional  (default)
    p_m is already conditioned on the leading digits being correct,
    so the dependence is carried by the conditioning and ρ is forced to 0:
        p_clean = p_b · p_m

--p-mag-mode marginal
    p_m is the marginal magnitude accuracy and ρ is the Pearson correlation
    of the two Bernoulli indicators:
        p_clean = clamp( p_b·p_m + ρ·√(p_b(1−p_b)·p_m(1−p_m)),
                         lo = max(0, p_b + p_m − 1),          ┐ Fréchet–
                         hi = min(p_b, p_m) )                 ┘ Hoeffding
```

Supplying both a conditional `p_m` and a non-zero ρ double-counts the
dependence, so the CLI rejects it. The predictors are **not** independent: on
this project's own simulated corpus, P(mag correct | pair correct) ≈ 0.902
against P(mag correct | pair wrong) ≈ 0.770, which implies ρ ≈ **+0.126**.
A positive ρ makes the attack *easier*, so ρ = 0 is the conservative choice —
but it is an assumption, not a bound.

Then, common to both modes:

```text
m_req = ⌈ ⌈log₂n / L⌉ · safety_factor ⌉
dim   = m_req + dim_overhead
```

**Signature supply is an explicit choice, not a hidden constant.** Earlier
versions derived the pool from a `surplus` multiplier and then back-computed
the raw-signature requirement, so scarcity never bound anything while `surplus`
silently swung the answer across ~11 orders of magnitude. The flag is gone.

```text
--supply unlimited  (default)      draws are i.i.d.
    q = p_clean^m_req · p_succ

--supply scarce --t-raw N          N = signatures available under the key d
    P(clean | pass) = p_clean · recall / pass_rate          ← Bayes
    T_filt          = ⌊ pass_rate · N ⌋
    C               ~ Binomial(T_filt, P(clean | pass))
    q               = C(C, m_req) / C(T_filt, m_req) · p_succ
```

`recall = P(pass | clean)` defaults to `pass_rate`, i.e. an **uninformative**
filter that only shrinks the pool. Raising it above `pass_rate` models a filter
that genuinely enriches the pool; the implied false-pass rate

```text
fpr = (pass_rate − p_clean·recall) / (1 − p_clean)
```

is derived and required to lie in `[0, 1]`, so inconsistent
`(pass_rate, recall, p_clean)` triples are rejected rather than ignored.

**The result is a distribution, not a point.** The number of reductions is
geometric, and in scarce mode the pool composition `C` is itself random, so the
model reports `p05 / p50 / p95` of `N` over the compound distribution instead of
substituting `E[C]` into a convex function. That substitution is a Jensen error:
for a 200-signature pool at `p_clean = 0.738` the 5–95% band spans roughly five
orders of magnitude, and the true expectation is dominated by rare bad pools.

**Reduction cost grows with lattice dimension.** With `--t-run-doubling-dims D`:

```text
t_run(dim) = t_per_run_sec · 2^((dim − dim_ref) / D)
time       = N · t_run(dim) / cores
```

Omitting `D` keeps the flat placeholder, and in that case the tool prints an
explicit warning that rows for different `L` are **not** comparable — a flat
per-run cost charges `L = 4` (dim 86) exactly what it charges `L = 8` (dim 44),
which inverts reality. Binomials are evaluated in log space via `lgamma`;
survival probabilities are evaluated in log space too, because `q` routinely
underflows float64. Parallelism is linear: each reduction is independent.

Defaults (machine-checked by `test_F8_readme_defaults_match_the_parser`):
`curve_bits=256`, `leak_bits=[6]`, `safety_factor=1.3`, `dim_overhead=2`,
`p_mag=82.0`, `p_mag_mode=conditional`, `correlation=0.0`,
`p_ml_start=80.0`, `p_ml_stop=99.0`, `p_ml_step=1.0`,

**`t_per_run_sec` is the single most important number in the model and it is not
measured here.** Calibrate it on your own hardware and solver — build a
synthetic all-clean HNP instance of dimension `m_req + 2`, run one `fpylll`
LLL/BKZ reduction, take wall-clock — then pass `--t-per-run-sec` together with
`--t-run-dim-ref` and `--t-run-doubling-dims`. Without all three, wall-clock is
order-of-magnitude only, which is why `--precision orders` is the default.

#### 3.10.1 What the cost model still does not capture

These are open gaps, not pending patches. Every one of them means the printed
figures are **not** a bound in either direction:

- **Confidence ranking is not modelled.** The model assumes a hard 0/1 label and
  draws uniformly random `m_req`-subsets. A real classifier emits calibrated
  scores, and an attacker would take the top-`m_req` most confident signatures,
  whose purity far exceeds the average `p_clean`. That is strictly cheaper by an
  unmodelled and potentially large factor, so the tables are **not** an upper
  bound on attacker cost.
- **`safety_factor` has no lattice-theoretic content.** `m_req · L ≥ log₂n` is
  necessary, not sufficient; whether `d` is actually a short vector is a
  determinant-versus-target-norm question (Gaussian heuristic, BKZ block size β)
  that this model does not evaluate. The `1.3` multiplier is a fudge standing in
  for that gap, and for small `L` (≲ 3) reduction fails regardless of `m_req`.
- **`p_reduction_success` defaults to 1.0**, i.e. an all-clean subset is assumed
  to yield `d` with certainty. It will not.

**And the load-bearing caveat, restated:** `p_b` — the probability the nonce-bit
oracle is right — is a swept input, not a capability anyone has demonstrated.
§3.9 shows the magnitude channel supplies a fraction of a bit, not the `L = 6`
the default table assumes. The tables are a sensitivity analysis of a
hypothetical, not a forecast.

`verify_x_candidate` is what makes a guess into a proven key rather than an
unchecked one.

**Removed:** `int_to_bytes`. It was dead code — nothing in the repository ever
called it — but `ecurve/__init__.py` kept re-exporting it, so `import ecurve`
raised `ImportError` and took every consumer down with it, including the test
suite that would otherwise have reported the problem. See §7.1.

### `ecurve/__init__.py`

Re-exports the names a caller actually reaches for, and nothing else. Everything
further stays addressable at its real home (`ecurve.secp256k1.mod_sqrt_all`, and
so on), because every duplicated name is another chance for the package surface
to drift from the modules. Pinned by `test_H1` … `test_H5`.

### `ecurve/k_magnitude.py`

`magnitude_distribution(lead, n) -> dict[int, float]` — exact conditional
distribution; `predict_magnitude(lead, n) -> Prediction(magnitude, probability)`
— its argmax (§3.9). The doctests reference `TEST_PARAMS` and are therefore
curve-specific; `test_E16` fails loudly when they drift.

### `ecurve/_ripemd160.py`

`ripemd160(data) -> bytes` — dependency-free fallback (§3.8).

### `generate_transaction_list.py`

Builds a signature corpus and emits a fixed-width report. The `_collect_rows`
function drives key generation, signing, the **simulated** predictor, and the
magnitude lookup. See §1 and §6.

### `ecdsa_attack_complexity.py`

Evaluates the cost model of §3.10 across an accuracy sweep and optional
`--leak-bits` values; prints a table per `L` and can emit CSV via `--csv`.
Signature supply is selected with `--supply {unlimited,scarce}`; `scarce`
additionally takes `--t-raw`, `--filter-pass-rate` and `--filter-recall`.
Reported counts are the `p05 / p50 / p95` quantiles of the number of
reductions, and wall-clock is order-of-magnitude unless `--precision full`.
Key helpers: `joint_clean_probability`, `bayes_post_clean`,
`log10_success_per_draw`, `runs_quantile`, `log10_t_run`, `min_raw_for_pool`.

## 5. Usage

`--curve-mode` defaults to **`legacy`** (real secp256k1) everywhere it appears.
Pass `--curve-mode test` explicitly to select `secp17k1`; expect it to be ~200×
faster and to answer a different question (§3.3.1).

The `test_A3_*` tests exercise the **import-sensitive** invocations below — the
modules run standalone from inside `ecurve/` and via `python -m ecurve.…` —
since those are the ones that used to break under the package-vs-flat import
ambiguity. The remaining commands are illustrative and are not each pinned by a
dedicated test.

```bash
# Regression suite (no dependencies) -- table output, see section 7
python3 tests/run_tests.py
python3 tests/run_tests.py -k filter        # only tests matching a substring
python3 tests/run_tests.py --list           # enumerate without running
python3 tests/run_tests.py --plain          # unittest's own text output
python3 tests/run_tests.py -v               # + full tracebacks on failure
python3 -m pytest tests/run_tests.py -q     # if pytest is installed

# Curve / sign / verify demo, standalone, as in the original project:
cd ecurve && python secp256k1.py > secp256k1.txt

# ... or as a module, from the repository root:
python3 -m ecurve.secp256k1

# Magnitude distribution on secp256k1 (§3.9); --curve-mode defaults to legacy:
python3 -m ecurve.k_magnitude                     # all leading pairs 10..99
python3 -m ecurve.k_magnitude --digits 47
python3 -m ecurve.k_magnitude --curve-mode test   # secp17k1, for comparison

# Signature corpus on real secp256k1, fixed key, BIP 143 preimages:
python3 generate_transaction_list.py \
        --private-key 64389052532870313044990203562685705333461655978490098671693221677551702405611 \
        --tx-per-key 5 --sig-type p2wpkh --outdir out

# Same, on the test curve — fast, reproducible via --seed:
python3 generate_transaction_list.py --curve-mode test --keys 3 \
        --tx-per-key 20 --seed 42 --outdir out

# Cost model — unlimited signature supply, uncalibrated flat placeholder:
python3 ecdsa_attack_complexity.py

# Scarce supply: 200 signatures exist under the target key, blind 50% pre-filter
python3 ecdsa_attack_complexity.py --supply scarce --t-raw 200 \
        --filter-pass-rate 0.5

# ... and with a pre-filter that actually enriches the pool (recall > pass rate)
python3 ecdsa_attack_complexity.py --supply scarce --t-raw 500 \
        --filter-pass-rate 0.9 --filter-recall 0.99

# Marginal p_mag with the correlation measured on this project's corpus (§3.10)
python3 ecdsa_attack_complexity.py --p-mag-mode marginal \
        --p-mag 88.88 --correlation 0.126

# Calibrated: cost scales with lattice dimension, so cross-L rows are comparable
python3 ecdsa_attack_complexity.py --leak-bits 4 6 8 \
        --t-per-run-sec 2.0 --t-run-dim-ref 58 --t-run-doubling-dims 12 \
        --cores 1 8 64 --precision full --csv complexity.csv
```

Note the explicit path in the `pytest` form. pytest only auto-discovers files
matching `test_*.py` or `*_test.py`, so a bare `pytest tests/` collects nothing
here and exits 5. To make the bare form work, add to `pytest.ini`:

```ini
[pytest]
python_files = run_tests.py test_*.py
```

Key flags for `generate_transaction_list.py`: `--curve-mode {test,legacy}` (default
`legacy`),
`--private-key`, `--keys`, `--tx-per-key`, `--min-start-range`,
`--ml-exp-accuracy`, `--seed`, `--outdir`, `--demo`, `--sig-type {p2pkh,p2wpkh}`.

## 6. Report format

`generate_transaction_list.py` writes
`transaction_list_<YYYYMMDDHHMMSS>.txt`: curve parameters, the signing formulas,
an explicit warning that the predictor is simulated, then a fixed-width table
with 13 columns:

```text
s, z, r(x), r(y), d*, k*, k^(-1)*,
ml_exp_k_val, ml_act_k_val, ml_match_k_val,
ml_exp_k_mag, ml_act_k_mag, ml_match_k_mag
```

Columns marked `*` are secret or secret-derived and exist only because this is a
simulation with full knowledge.

The statistics block reports the effective key count, transactions per key, the
**actual** number of rows generated, the tuple-space cardinality `(n−1)⁴`
(a combinatorial ceiling, *not* a security bound), the assumed vs. realised
predictor accuracies (with the INPUT ASSUMPTION caveat on the k_val rate), the
observed distribution of decimal lengths of `k` as `k_mag_<n>_count`, and
elapsed time.

Accuracy is computed as `matches / len(rows)`. If it drifts from
`--ml-exp-accuracy`, that is sampling noise, nothing more — the mask is
constructed to hit the target exactly.

## 7. Verified invariants

`tests/run_tests.py` holds **78 tests** built on `unittest`, grouped into
`TestCase` classes by concern. The default runner prints a table; each class
docstring supplies a section heading and each method name carries the audit ID
it regresses (`A1`, `B3`, `F2`, `G9`, `H3`, …). It runs in about one second.

**What is pinned as a literal and what is derived.** Anything fixed by an
external specification stays a literal: the RFC 6979 vectors, the RIPEMD-160
digest of `b"abc"`, the `m_req` formula. Anything that is a *project choice* is
read from the source of truth at runtime — curve orders, private keys, digit
counts. An earlier revision hardcoded the test curve's order and a private key
valid only for it, so swapping `TEST_PARAMS` broke four tests that had nothing
to do with the change.

Enforced by the suite:

- RFC 6979: 3/3 official secp256k1 + SHA-256 test vectors exercised by the suite.
- RIPEMD-160 / HASH160: known-answer digests for `b"abc"` pinned, exercising the
  pure-Python fallback path (§3.8). (The broader "all official vectors + block-
  boundary fuzzing" verification of `_ripemd160.py` is a development-time check,
  not part of this suite.)
- `verify(sign(m)) = True` on both curves over repeated trials.
- Generated public keys lie on the curve, on both parameter sets.
- `n·G = O`; `scalar_multiply` returns `None` (never `(0,0)`) for infinity.
- `P + (−P) = O` returns `None` and `verify_signature` survives it.
- **Curve parameters themselves** (`test_G1` … `test_G8`, §3.3): `G` on the
  curve, `n·G = O`, `(n−1)·G = −G`, `n` and `p` prime, non-singular, Hasse
  bound, and a `p − n` gap wide enough to make the coordinate path reachable.
- **Negative cases**, which mutation testing showed were entirely absent:
  `is_on_curve` rejects off-curve points (`test_G10`); `verify_signature`
  rejects an off-curve or `None` public key *before* touching scalar
  multiplication, which is what stops invalid-curve attacks (`test_G11`); a
  tampered `r`, `s` or `z` is rejected rather than merely returning some bool
  (`test_G12`).
- **Package surface** (`test_H1` … `test_H5`, §7.1): every name in
  `ecurve.__all__` resolves, re-exports are the same objects as the modules'
  and `__init__.py`'s import list is diffed against the modules statically.
- `magnitude_distribution` sums to 1 on both curves; `k_magnitude` doctests
  pass; and the predictor's degeneracy is asserted curve-independently — one
  magnitude covers at least 88 of the 90 leading pairs (`test_E21b`).
- Argument validation rejects out-of-range inputs on both entry points:
  `generate_transaction_list.py` (`--keys 0`, negative `--keys`, `--private-key`
  outside `[1, n-1]`, `--ml-exp-accuracy` outside `[0, 1]`, `--min-start-range ≥ n`)
  and `ecdsa_attack_complexity.py` (non-positive `--safety-factor`,
  `--t-per-run-sec`, `--curve-bits`, `--leak-bits`, `--cores`, `--p-ml-step`
  and `--t-run-doubling-dims`; negative `--dim-overhead`; `--p-mag` and
  `--p-reduction-success` outside their ranges; `--correlation` outside
  `[-1, 1]`).
- Cost-model structure, under `test_F*` (§3.10): the unlimited-supply case
  equals the i.i.d. limit `p_clean^m_req`; the Bayes filter leaves purity
  unchanged when uninformative, raises it when informative, and rejects
  inconsistent `(pass_rate, recall, p_clean)` triples; `--filter-pass-rate`
  demonstrably reaches `runs`; per-run cost doubles every `D` dimensions and is
  flat without `D`; `--p-reduction-success` enters the denominator; `p_clean`
  never escapes the Fréchet–Hoeffding bounds over a 60-point grid; reported
  quantiles are ordered and the median matches `ln2 / q` in closed form; a
  fully clean pool (`q = 1`) does not raise; `--filter-recall` defaults to
  uninformative; an undersized pool yields the required `T_raw` instead of a
  bare `n/a`; and the README's declared defaults are diffed against the
  parser.
- The import-sensitive invocation modes (standalone from `ecurve/` and
  `python -m ecurve.…`) import and run, under `test_A3_*`.

### 7.1 Two failure modes the suite cannot test, and what replaces them

**A broken `ecurve/__init__.py` stops the suite from loading at all**, so no
test can report it — the traceback names the symbol but not the fix, and points
at the module that is innocent rather than the one that is stale. `run_tests.py`
therefore wraps its imports in a diagnostic that names the offending file and
line, offers the two possible repairs, and exits 2 (distinct from 1, which means
tests failed). This is what the `int_to_bytes` removal (§4) surfaced.

**A test runner can hide failures.** unittest reports a failing
`self.subTest(...)` block through `addSubTest` and then does *not* call
`addSuccess` for the parent test. A result class that only overrides
`addSuccess`/`addFailure`/`addError` records nothing for that test: the row
vanishes, the FAIL count stays at zero, and the summary prints ALL GREEN over a
real failure. Dozens of tests here use `subTest`, and this bug was live long
enough to make four genuine failures invisible. The table runner now handles
`addSubTest` explicitly, treats a test that reports no outcome as an ERROR
rather than dropping it, and cross-checks its row count against
`result.testsRun` before printing a verdict.

### 7.2 Mutation testing

"All tests pass" says nothing about whether the tests could fail. Injecting
plausible defects and counting which tests notice:

| Injected defect | Tests that catch it |
| --- | --- |
| Drop `x₂` from `x₃ = λ² − x₁ − x₂` | 5 |
| `is_on_curve` returns `True` unconditionally | 2 (`test_G10`, `test_G11`) |
| `r_y = y % n` (bug B6) | 1 (`test_B6`) |
| Drop the on-curve guard in `verify_signature` | 1 (`test_G11`) |
| Drop `+ a` from the doubling slope | 1 (`test_G9`, §3.3.1) |
| `3x² + 2a` — subtle corruption of the same term | 1 (`test_G9`) |
| `3x² − a` — subtle corruption of the same term | 1 (`test_G9`) |

The last three rows are caught by `test_G9` alone: with `a = 0` on both shipped
curves, they are arithmetically invisible everywhere else in the suite.

Two further mutations are **not** caught, and both are provably **equivalent
mutants** rather than coverage gaps — `test_G13` pins the property that makes
them so:

- `point_add`'s inverse test. The old form `x₁ = x₂ and y₁ ≠ y₂` diverges from
  `(y₁ + y₂) ≡ 0 (mod p)` only at `y₁ = y₂ = 0`, i.e. a point of order two. A
  group of odd prime order has none.
- `scalar_multiply`'s skipped final doubling is an optimisation; the discarded
  point cannot affect the result.

## 8. Known limitations

- **Not constant-time, not side-channel resistant, not production code.** The
  ladder is deliberately non-constant-time (§3.5). Do not use any of this to
  protect real funds.
- Test-mode `z` is not bound to the message (§3.8), so `mode="test"` is not a
  signing oracle. This also means the test curve cannot exercise RFC 6979, which
  leaves the most delicate cryptographic code in the repository covered only by
  the 200×-slower curve (§3.3.1).
- **Neither shipped curve exercises the `a` term** in the doubling slope, since
  both set `a = 0`. `test_G9` pins the *formula* differentially (§3.3.1), but no
  test pins the group-law *invariants* for `a ≠ 0` — that would need parameters
  which genuinely are such a curve. Anyone reusing `ecurve/` with `a ≠ 0` is
  running a path the shipped parameters never touch.
- `mode` branching appears in ~10 places; each is a site where the two curves can
  drift apart.
- `maximum_transaction_count = (n−1)⁴` has no defined security meaning.
- `ecurve/__init__.py` is a hand-maintained export list, and so is this README.
  Both have drifted from the code before. The machine-checked parts are the
  cost-model defaults block (§3.10) and the package surface (§7.1); the prose
  around them is not pinned by anything and should be treated as the least
  trustworthy artefact in the repository.
- The cost model's `t_per_run_sec` is uncalibrated unless you pass it, and the
  dimension-scaling model is opt-in via `--t-run-doubling-dims`; without it,
  rows for different `L` are not comparable and the tool says so (§3.10).
- The cost model omits confidence ranking, has no lattice-theoretic content in
  `safety_factor`, and assumes reductions on clean subsets always succeed. It is
  therefore **not a bound in either direction** (§3.10.1).
- **The predictor is simulated (§1).** This is not a code defect to be patched;
  it is the methodological boundary of the project.
