#  WHAT THIS TABLE IS  --  read before quoting any number
#
#  A COST ESTIMATE for a HYPOTHETICAL attack, not a demonstration and
#  not a break. Every row ASSUMES an oracle that already predicts the
#  top bits of each secret nonce at the stated accuracy. No such oracle
#  exists for a correct ECDSA implementation; building one is equivalent
#  to (partially) solving the elliptic-curve discrete log (~2^128 work),
#  which this script does NOT attempt.
#
#  So a row like '90% -> ~1 year' does NOT mean secp256k1 breaks in a
#  year. It means: GIVEN a 90%/82% nonce-bit oracle, the lattice
#  book-keeping alone would take ~1 year on 1 core. The oracle is the
#  hard part and is assumed for free.

HOW TO READ EACH COLUMN
--------------------------------------------------------------------------------------------------------
  p_ml%        accuracy of the leading-digit predictor p_b. This is
               the SWEPT variable: each row is one assumed accuracy.
  p_clean      chance a single signature is usable (both predictors
               right) = p_b * p_m. One bad signature spoils a batch.
  m_req        signatures that must ALL be clean in one batch (= 56 here).
  odds/try     chance that ONE random batch is 100% clean, PER TRY
               (= q). '1 in 24.5M' = each attempt has a 1/24,500,000
               chance. This is NOT the total you need -- it is the odds
               of a single coin flip.
  reductions   how many attempts (coin flips) until the first success.
    N:lucky5%  This is a COUNT OF ATTEMPTS, not a combination C(.,.),
    N:median   and it has NO MAXIMUM. Being a 1-in-q coin, N VARIES:
    N:avg        lucky 5% = you finish unusually early,
    N:bad95%     median   = half the runs finish by here,
               avg      = the long-run average (equals the odds number),
               bad 95%  = 5% of runs still run PAST here.
               So N:bad95% is LARGER than N:avg. That is expected for a
               geometric process, not a contradiction.
  t @ N cores  wall-clock = reductions * seconds-per-reduction / cores,
               at the MEDIAN N, for N cores in [1, 8, 64].
               Units: s, min, h, d (day), mo (month), yr (year).
  NUMBER FORMAT: '16K'=16 thousand, '16M'=million, '13B'=billion,
               '2.5T'=trillion; above that, standard sci '4.0e17'.
  POOL SIZE: unlimited mode is the best-case infinite-pool limit;
             a batch of exactly m_req clean signatures cannot be
             guaranteed from a tiny pool. Run  --supply scarce
             --t-raw N  to size the actual signature pool you need.

Unvalidated assumptions carried by EVERY number above
--------------------------------------------------------------------------------------------------------
  - p_b is an assumed oracle accuracy, not a measured capability (recovering it is a partial ECDLP)
  - safety_factor is a fudge with no lattice-theoretic justification
  - confidence ranking is not modelled; a real attacker would do better
  - t_per_run_sec must be calibrated on your own hardware and solver

  Bottom line: this estimates the CHEAP half of the attack (the
  lattice book-keeping, which parallelises trivially). The EXPENSIVE
  half -- the nonce-bit oracle -- is assumed, and for a correct
  implementation it costs ~2^128, which no number of cores shortens.
